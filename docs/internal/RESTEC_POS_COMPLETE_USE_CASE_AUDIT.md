# Restec POS complete use-case audit

## Phase 4 update

The Phase 4 rerun updates the normal-payment rows in the normative CSV, especially UC-025 through UC-044, UC-053 through UC-056, UC-061/062, and UC-081 through UC-086. The prior expiry finding is resolved at application/domain level: browser/local time no longer terminalizes money, scheduler reconciliation queries provider state, authoritative terminal reads commit through the shared reservation/inbox/outbox boundary, different technical observations reuse one logical POS event, and uncertain outcomes retain capacity. Completed-only traditional semantics and all approved two-way/three-way mixed combinations are now explicit and locally tested.

Current local evidence is 121 tests: 116 passed and five explicitly gated, plus mock E2E 4/4, targeted Phase 1/3/4 lifecycle 54/54, typecheck, 12 migration structural checks, OpenAPI/public artifact validation, docs validation, examples, and full build. Real PostgreSQL execution, provider sandbox semantics, and deployed scheduler execution remain gated; the verdict therefore remains not ready for production certification.

Updated scoped readiness is evidence-based rather than a row-count restatement: functional completion 82%, pilot readiness 58%, and production readiness 34%. Pilot/production remain capped by the Phase 2 database gate, missing retained provider/deployed-cron evidence, and the operational/Phase 5 gaps documented below.

## Executive verdict

Restec has a coherent canonical v1 API, strong request authentication, strict monetary schemas, a mock-tested hosted-payment path, and an inbox/outbox delivery design. It is **not ready for a real POS pilot or production activation** because the repository does not prove the Supabase runtime path, real provider path, real POS behavior, production isolation, or operational recovery. There are also unresolved critical functional gaps: cross-channel/concurrent payment races can create private/downstream effects before the local financial lock, permanent table QR/current-bill resolution is absent, webhook-secret rotation is absent, refund/reversal coverage is incomplete, and several recovery actions only audit rather than restore convergence.

The audit found **100 distinct use cases and edge cases**. The complete 16-field record for every case is the companion CSV [RESTEC_POS_USE_CASE_MATRIX.csv](RESTEC_POS_USE_CASE_MATRIX.csv). The index in this report preserves the case/status/risk/evidence mapping; the CSV is normative for actor, preconditions, exact flow, endpoint/event, state transition, idempotency/retry, security boundary, missing work, and exact certification test.

No runtime or financial logic was modified. Only this report and the CSV matrix were generated.

## Runtime/data findings

### Authentication and isolation

The public middleware requires a syntactically valid unique request ID, Bearer key, JSON content type even on signed GET, <=1 MiB body, timestamp tolerance, exact HMAC and durable replay reservation (`apps/api/src/auth.ts:13-117`). Keys are environment-prefixed and scrypt-hashed; signing/configuration secrets use AES-256-GCM (`packages/security/src/index.ts:54-83`). Location scope is checked in middleware and restaurant ownership is rechecked in the Supabase join (`apps/api/src/auth.ts:77-83`; `packages/database/src/supabase-repository.ts:240-283`).

The optional IP/mTLS requirements stored during provisioning are not enforced by public authentication. `allowed_ip_cidrs` and `mtls_subjects` are persisted (`supabase/migrations/20260802000100_pos_partner_credentials.sql:11-18,151-160`), but `authenticateApiKey` does not select or check them (`packages/database/src/supabase-repository.ts:102-137`).

### Bill and payment atomicity

Phase 1 introduces one bill-scoped financial reservation boundary. Existing-bill revisions, external payments, and digital sessions reserve under the bill lock before downstream calls; authoritative session events atomically convert or release their reservation with inbox/outbox work. In-memory real-HTTP and 100-request stress tests prove losing requests do not reach the downstream mock. The remaining certification gap is execution of these RPCs under real PostgreSQL concurrency and injected crash windows.

The bill contract validates arithmetic but not lifecycle transitions. `status`/order status enums are accepted and forwarded; no local bill transition state machine prevents reopening a terminal bill (`packages/contracts/src/index.ts:33-74`; `apps/api/src/app.ts:180-214`).

### Payment sessions

Session creation checks payable/reconciled state, amount/currency, deterministic identity, active-session persistence, provider URL allowlist/DNS, encryption and audit (`apps/api/src/app.ts:274-423`). Checkout refresh uses a DB lease and safe redirect (`apps/api/src/app.ts:536-646`). Authoritative private events enforce connection/location/session/bill/amount/currency/method/status associations before the atomic inbox/session/bill/outbox RPC (`apps/api/src/app.ts:909-1053`; `supabase/migrations/20260731000100_private_event_identifier_validation.sql:10-125`).

Expiry is inconsistent: the browser route transitions an expired actionable session, the authenticated status route merely returns stored state, and reconciliation audits an expired session without transitioning it (`apps/api/src/app.ts:424-447,541-548`; `apps/api/src/reconciliation.ts:83-101`).

### Outbox, retries and dead letters

Outbox claim uses `FOR UPDATE SKIP LOCKED` and expiring leases (`supabase/migrations/20260717000100_restec_foundation.sql:26`). Delivery accepts 200/201/202/204, retries network/408/425/429/5xx, records attempts, and dead-letters after the configured maximum (`packages/connectors/canonical-rest/src/index.ts:47-75`; `apps/api/src/app.ts:1079-1188`). These guarantees were not executed against Supabase during this audit.

Webhook destination SSRF filtering resolves DNS before delivery, but fetch performs a separate resolution; DNS rebinding/pinning is not comprehensively closed (`packages/webhook-delivery/src/index.ts:31-49`; `packages/connectors/canonical-rest/src/index.ts:51-64`).

## Contradictions and artifact drift

1. **Illegal bill transition claim vs runtime.** Partner docs say an illegal terminal transition is rejected (`docs/pos-partner/BILL_AND_ORDER_SYNC.md:18`), but the runtime only validates enums/version/paid floor and forwards the snapshot; there is no bill lifecycle transition table (`packages/contracts/src/index.ts:33-74`; `apps/api/src/app.ts:180-214`).
2. **“Refresh private bill” is not a refresh.** The internal schema exposes `refresh_private_bill` and audit says refreshed, but execution calls the same read-only compare method and does not update either side (`apps/api/src/app.ts:1198-1200,1221-1234`; `apps/api/src/reconciliation.ts:21-53`).
3. **Rate-limit documentation overstates behavior.** Docs say configurable limits and stricter budgets for multiple operations (`docs/RATE_LIMITS.md:3`). Runtime hard-codes 100/min per credential/location/path and 20/min auth-failure, does not rate-limit credential changes/replay because those are protected internal/operator operations, and ignores `limited.allowed` in the auth-failure branch (`apps/api/src/auth.ts:33-69`).
4. **Webhook endpoint table vs runtime configuration.** Provisioning writes both `webhook_endpoints` and embedded `pos_connections.encrypted_configuration` (`supabase/migrations/20260802000100_pos_partner_credentials.sql:139-160`). Runtime delivery ignores `webhook_endpoints` and reads URL/secret from decrypted connector configuration (`packages/database/src/supabase-repository.ts:264-282`; `packages/connectors/canonical-rest/src/index.ts:44-60`).
5. **Required webhook master key is unused.** Production config requires `RESTEC_WEBHOOK_MASTER_KEY` (`apps/api/src/config.ts:39,67-71`), but bootstrap/runtime never consumes it (`apps/api/src/bootstrap.ts:8-43`).
6. **OpenAPI reconciliation enum omits a runtime value.** OpenAPI allows matched/mismatch/review_required (`openapi/restec-pos-partner-v1.yaml:567`), while runtime types and reconciliation can produce `pending` (`apps/api/src/reconciliation.ts:3,34-46`; `packages/database/src/repository.ts:87` is an unconstrained string).
7. **Postman/OpenAPI validate only represented routes.** Artifact validation passes, but neither artifact contains QR/current-bill resolution, terminal identity, POS refund/void/reversal or credential/webhook rotation because the runtime does not expose them (`postman/Restec-POS-Partner-v1.postman_collection.json:39-151`; `openapi/restec-pos-partner-v1.yaml:24-247`).
8. **Remote-sandbox naming overstates coverage.** `test:remote-sandbox` includes a file whose only remote API assertion is health (`apps/api/src/sandbox.e2e.test.ts:3-9`); the DB tests are gated/skipped without credentials.

## Ten highest-risk missing or incomplete scenarios

1. **UC-036/UC-041/UC-042/UC-043 — real database certification:** the shared pre-effect reservation implementation passes memory/HTTP stress but has not run against PostgreSQL or provider crash injection.
2. **UC-085 — database failure windows:** durable ambiguity exists, but failure at every RPC statement and stale-idempotency recovery remain unexecuted.
3. **UC-086 — provider timeout after actual success:** mock ambiguity protection passes; a real provider-side success followed by response loss is not yet certified.
4. **UC-045 through UC-048 — refund/void/reversal/chargeback:** only provider refund notification skeletons exist; initiation and broader lifecycle are absent.
5. **UC-022/UC-024 — permanent QR/current bill and table reuse:** missing functionality also creates a cross-guest privacy risk.
6. **UC-003/UC-071 — webhook-secret rotation:** no grace/version binding; queued events can fail across rotation.
7. **UC-056/UC-083 — missing provider event and stale expiry:** reconciliation audits but does not safely converge terminal state/notify POS.
8. **UC-060/UC-085/UC-087/UC-096 — DB/scheduler/worker failure:** core lease/transaction code is unexecuted against Supabase and lacks chaos/alert evidence.
9. **UC-074 — sandbox/production infrastructure separation:** required by docs but not proven by repository evidence.
10. **UC-099 — offboarding with pending money/events:** disabling access can strand required financial notifications; no drain policy exists.

## Ordered implementation plan for every critical/high gap

1. **Create one authoritative payment ledger/reservation boundary.** Reserve bill balance before private/provider mutation; serialize external and digital commitments; introduce a saga/outbox and compensating reconciliation for uncertain downstream outcomes. Close UC-012, UC-033-044 and relevant UC-085/086.
2. **Run and expand Supabase integration tests.** Make inbox/outbox/session tests mandatory; add concurrent bill/external/mixed payment, idempotency crash, lease reclaim and post-HTTP-success crash cases. Close certification gaps across UC-009-012, UC-025-027, UC-041-044, UC-053-060, UC-096.
3. **Define and implement payment correction lifecycle.** Product-approve full/partial refund, void, reversal, chargeback and dispute authority/status/arithmetic; add ledger events, APIs where needed, schemas, reconciliation and webhooks. Close UC-045-048.
4. **Implement table session and permanent QR lifecycle.** Add opaque stable tokens, atomic one-current-bill binding, move/close/reuse semantics, cache rules, enumeration protection and cross-guest privacy tests. Close UC-020-024.
5. **Make expiry and missing-event recovery authoritative.** A scheduled transaction should expire eligible sessions, create exactly one event, and notify POS; terminal private status without webhook needs a controlled synthesis/recovery queue. Close UC-028, UC-056, UC-082/083.
6. **Implement versioned webhook configuration and rotation.** Make one source of truth, bind queued attempts to a secret version or dual-sign policy, support grace/rollback/audit, and remove or use the master key. Close UC-003, UC-069-072.
7. **Finish reconciliation as a durable case system.** Fix/remove fake refresh action; persist mismatch/review state, assignment, evidence and resolution; make requeue eligibility/audit explicit. Close UC-052, UC-077-080.
8. **Harden onboarding/offboarding.** Add existing-partner location workflow, terminal model decision, bulk revoke/disable, pending-event drain/quarantine, re-onboarding/retention rules and operator approval/audit. Close UC-001-008 and UC-097-100.
9. **Close infrastructure isolation and operations gates.** Prove separate projects/IAM/secrets, migration attestation, backup restore, RPO/RTO, scheduler failover, queue-age/dead-letter alerts and incident drills. Close UC-060, UC-074, UC-085, UC-087/088.
10. **Harden capacity and edge security.** Fix auth-failure limiter outcome handling and trusted proxy logic; enforce or remove stored IP/mTLS policies; add backoff/jitter/circuit breaker, DNS pinning decision and production-like load tests. Close UC-057/058, UC-093-096.
11. **Resolve artifacts after runtime decisions.** Correct bill transition, reconciliation, rate-limit and reconciliation-status claims; add all new routes/events to OpenAPI/Postman/UAT and test the docs examples.
12. **Certify externally in order.** Local DB integration -> remote Restec sandbox -> real provider sandbox -> standalone vendor simulator -> real POS partner UAT -> controlled production canary -> retained live reconciliation evidence. No readiness label should advance on prerequisite-only scripts.
